很多人問我們 [React Flow](https://reactflow.dev/) 是否會移植到他們喜愛的前端框架。有兩個人甚至創建了自己的函式庫（[Svelvet](https://www.svelvet.io/) 和 [Vue Flow](https://vueflow.dev/)），都將 React Flow 作為起點。儘管在其他框架中對這類工具有明顯的需求，但我們一直堅持使用 React，直到最近。

今年初，我們覺得有時間和空間來選擇接下來要做什麼。最後我們花了接下來的幾個月開發 [Svelte Flow](https://www.svelteflow.dev/) 並在本月初推出。這自然引出了一個問題：

## 為什麼選擇 Svelte？

### 1. 新聞編輯室的根源

在開發 React Flow 之前，我們以 [webkid](https://webkid.io/) 的名義與新聞編輯室合作製作了許多互動式資料視覺化。在那段時間，我們看到了 Rich Harris 在紐約時報的作品（[像這個](https://www.nytimes.com/interactive/2018/01/27/technology/social-media-bots.html)），並從一開始就關注 Svelte 的發展。

2020 年，我們在一個專案中嘗試使用 Svelte 來建立互動式地圖（如下），使用體驗非常好。它給我們留下了很好的印象，我們很興奮能夠再次使用它。

### 2. 快樂且不斷成長的社群

儘管 Svelte 的使用量不到 React、Vue 或 Angular 的一半，但根據 [2022 年 JavaScript 現況調查](https://2022.stateofjs.com/en-US/libraries/front-end-frameworks/)，它具有很高的保留率、使用率和關注度。我們聽到很多傳聞證據說開發體驗很棒，我們很高興能親身體驗。此外，最近來自 [Vercel 的資金](https://vercel.com/blog/vercel-welcomes-rich-harris-creator-of-svelte)讓我們更有信心 Svelte 核心團隊會繼續維護下去。

### 3. 我們就是...想要？

本著實驗的精神，我們在幾週內建立了 Svelte Flow 的第一個原型。它成功了，而且我們做得很開心。當這些衝動來臨時，我們喜歡跟隨它們，所以我們繼續前進。

使用 Svelte 很不一樣，因為它是一個編譯器，並且內建了很多很棒的功能。我們特別喜歡它帶有作用域樣式、內建 stores 和易於理解的反應系統。也有一些仍然感覺奇怪的東西，例如處理事件或使用 TypeScript 對元件進行型別定義，但那是另一篇部落格文章的內容 :)

## 為什麼不堅持使用 React？

我們從支付 React Flow Pro 的資助組織獲得財務穩定，這取決於 React 作為行業標準的普及性。框架確實會[消亡](https://stackoverflow.blog/2018/01/11/brutal-lifecycle-javascript-frameworks/)，能夠將我們的函式庫移植到其他語言意味著我們作為公司更加靈活，而不是依賴 React（以及 Meta）的成功。

## 那麼進展如何？

發布進行得_非常_順利。我們在很多電子報和首頁上被推薦。我們在發布時更改了 Github 儲存庫名稱（從 react-flow 改為 [xyflow](https://xyflow.com/)），人們似乎對品牌重塑感到興奮，沒有看到一根乾草叉。而且已經有[專案](https://svelteflow.dev/showcase)在實際應用中使用 Svelte Flow。太棒了。

此外，在這個過程中，我們重構了函式庫的核心，將其中很大一部分抽象為 vanillaJS，修復了沿途發現的錯誤，使兩個函式庫都受益。我們對此也非常滿意。

總而言之，我們很興奮將 Svelte Flow 帶入測試版發布，並期待看到人們用它建立什麼。我們下次見！
